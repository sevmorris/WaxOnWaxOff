### The app now tells you when loudness normalization does something other than what you asked for

WaxOff asks `loudnorm` for a single constant gain, so your mix keeps its dynamics and only its level changes. That is a *request* FFmpeg can refuse. When it refuses — because the mix's loudness range is wider than the target, or because a constant gain would breach the true-peak ceiling — it silently applies time-varying gain instead. The file lands under its target with its loudness range squeezed, which is the exact processing the setting exists to avoid.

v2.4.0 documented that this can happen. It gave you no way to know whether it had happened to your file.

It does now. The measurements from the analysis pass are checked against FFmpeg's own condition before the second pass runs, and the console says which one failed — loudness range, or true-peak headroom. This is detection only: no audio is processed differently than in 2.4.0.

The same check runs in WaxOn, where the wider `LRA=20` makes it far less likely but the true-peak condition can still fire.

### WaxOff no longer leaves a temp fragment in your MP3 title

In **MP3-only** mode the ID3 title came out as something like `episode-lev-18LUFS.1a2b3c4d` — the encoder was reading the title from an internal temporary filename. That title travelled into the podcast feed and showed in every player.

The title now comes from the delivered filename, identically in both output modes. **Both** mode was never affected, and no built-in preset selects MP3-only, so you only hit this by choosing it deliberately.

### WaxOn warns before folding a surround source to stereo

A 5.1 or 7.1 file processed with Channels = Stereo is folded to two channels by FFmpeg's default matrix. The mono path already told you when it did the equivalent; the stereo path did it silently. There is now a console warning and a `MULTI→STEREO` badge in the file list, matching the existing `MULTI→MONO` and `STEREO→MONO` badges.

### WaxOff queues read correctly

Delivery processes several files at once, and the processing readout was a single shared line that showed whichever file had reported most recently — attributed to no file in particular. On a queue it was wrong the whole time.

Each row now shows its own stage, and clears when that file finishes. Output verification, which runs after files are written, has moved to the toolbar as "Verifying delivered files… N done". Between them, that removes the stale "Encoding MP3…" that used to sit on screen for a minute or more after the encode had finished and the file was already on disk.

### Also in this release

- The WaxOn disk-space pre-flight reserved more temp space than the pipeline uses, and on a nearly-full disk could block a batch that would have fit. Corrected.
- The manual now documents WaxOff metadata handling, and the README states the build floor for anyone compiling from source: Xcode 26 or later.

### Under the hood

CI had been red since 9 July and through two releases — the pinned Xcode was a version older than the code required. It is green again, `release.sh` now refuses to cut a release from a commit CI has not proven green, and the build is warning-free for the first time: 188 concurrency warnings down to zero, which unblocks a future move to the Swift 6 language mode.

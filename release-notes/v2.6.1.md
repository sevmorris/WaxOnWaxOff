### Three fixes to how the toolbar behaves

Pressing Process twice while WaxOff was switching from one batch to the next could start a second delivery the app then lost track of — still rendering, but with no progress shown and no working Cancel. The gap it slipped through was short, and it was exactly the moment the button looked unresponsive, which is when people press again. The toolbar now reads "Starting next batch…" there and ignores the second press.

The first batch you ever process no longer leaves the toolbar looking stuck. Both modes waited on the completion notification before clearing their running state, and on a Mac that has not yet answered the notification prompt, that wait lasts until you answer it — so a finished delivery sat there looking busy, behind a system dialog that is easy not to connect to the app. Nothing waits for the notification now.

Clear and Remove are unavailable while a batch is delivering. A batch works from the file list as it stood when you pressed Process, so clearing it mid-run stopped nothing: files kept landing on disk while the rows tracking them vanished. Both stay available during verification, where the files are already written.

### The verification pass is documented

2.6.0 added a distinct state for the pass WaxOff runs after delivery, and the ability to start the next batch during it, then described neither. The manual and in-app Help now cover what the pass is, why every row reads Complete while it runs, and what Stop verifying actually stops.

### A correction in the vendor notes

`Vendor/README.md` said in one place not to delete the bundled-FFmpeg releases, and recorded in another that one of them had been deliberately withdrawn for licensing reasons — the first reading as the rule and the second as a mistake to undo. The rule now names the release it protects, and the withdrawn one is marked as not to be restored.

Nothing in the signal chain changed. Files delivered by 2.6.1 are identical to those delivered by 2.6.0.

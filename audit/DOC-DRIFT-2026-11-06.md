# Documentation Drift Audit — 2026-11-06

**Scope:** `README.md`, `docs/index.html` (landing page), `docs/manual/index.html` (manual), `docs/manual/theory.html` (theory), `WaxOnWaxOff/Views/HelpView.swift` (in-app Help), `Vendor/README.md`, `CHANGELOG.md` — audited against the implementation at `2e53f0b` (v2.17.0, working tree clean).

**Method:** version surface reconciled across code, tags and docs; internal links and anchors checked mechanically across the three HTML documents; every external URL probed; each mode's behavioral claims verified against `AudioProcessor.swift`, `DeliveryProcessor.swift`, `FFmpegFilters.swift`, `ProcessingConfig.swift`, `OutputAllocator.swift` and the views; then a reverse sweep for 2.13–2.17 behavior no document mentions. Line numbers below are as found at `2e53f0b`.

**Ground rule applied:** code is the truth. DSP design was not evaluated — only whether the documents describe what the code does.

It changed four lines in the manual and about a dozen in the theory page, and missed the rest. Every WRONG sentence below predates that commit (checked with `git blame`). Everything 2.13–2.17 changed is documented: the mono/stereo limit in WaxOff, the removal of ISP (est.), macOS 15, the Original Files switch, presets keeping changes and leaving the output folder alone, and self-update.

## 3. Findings

### WRONG — claims the code contradicts

**F-W1 · `docs/manual/index.html:720`** — WaxOn's Loudness Normalization pipeline step: "EBU R128 normalization in two passes", pass 1 measuring LRA and threshold, "loudnorm applies dynamic normalization" when headroom is short. WaxOn measures once with `ebur128` and applies `target − integrated` as one gain (`AudioProcessor.swift:302-312`). The same manual's settings table (`:676`) already said so.

**F-W2 · `docs/manual/theory.html`, WaxOn described as running loudnorm** —
- `:567` "Both modes pass an LRA value… both WaxOn and WaxOff set `linear=true`", directly above `:568`, which says WaxOn runs no loudnorm.
- `:575` "Both WaxOn and WaxOff solve this with a two-pass approach."
- `:601` "Both WaxOn and WaxOff request linear mode for pass 2."
- `:604` "WaxOn's `LRA=20` makes it much less likely".
- `:802`, `:816–819` "loudnorm analysis" in WaxOn's placement and stage-order rationale.
- `:1000` "Actual normalization uses FFmpeg's `loudnorm` filter in a two-pass pipeline", unscoped; `:1004`, `:1008` likewise.
- `:1141` silent input: WaxOn has no loudnorm pass 1 to report `-inf`; its `ebur128` reading floors at −70 LUFS and WaxOn applies no gain (`AudioProcessor.swift:304-316`).
- Summary `:1184` "Two-pass loudnorm with linear=true" unscoped; `:1192–1193` "LRA=20 in WaxOn".

**F-W3 · `docs/manual/theory.html`, WaxOn's ceiling called true-peak with Loudness Norm on** — `:461` "always enforces a fixed −1.0 dBTP true-peak ceiling — via a standard peak limiter when Loudness Norm is on"; `:651` the limiter's `limit` is "the linear-amplitude equivalent of −1.0 dBTP"; `:1075` Defaults "Fixed −1.0 dBTP"; `:1196–1197` Summary "Always-enforced true-peak ceiling". With Loudness Norm on, `alimiter` runs at the native rate and holds sample peaks at −1.0 dBFS (`AudioProcessor.swift:155-160`, `:320-322`), as the same page says at `:490` and `:841`. The 2026-08-25 audit's F-W3 found this conflation in the README and landing page; these copies survived.

**F-W4 · `docs/manual/theory.html:763`** — "Unlike the RNNoise stage (which requires an explicit per-channel split…)". RNNoise left the app in 2.8.0.

**F-W5 · `docs/manual/index.html:1124`** — Tips, Mono vs. Stereo: for "both microphones in one stereo file, set Channels to Stereo". That recording is what Split L/R (2.10.0) exists for; Stereo keeps both speakers in one file under one shared gain, the imbalance Split L/R removes.

### MISSING

**F-M1 · `docs/manual/index.html:651`** — Source Channel "is not available when Channels is Stereo". It is unavailable in Split L/R too (`SettingsView.swift:140`). Help said nothing about when it is unavailable.

**F-M2 · `docs/manual/index.html:523`** — the badge list omits `MULTI→STEREO` (Stereo, more than two channels) and `1 FILE` (Split L/R, mono source) (`FileListView.swift:56`, `:67`). No document mentioned either.

WaxOff has a Preset definition (with "(Modified)" and the output-folder rule) and a Built-in Presets section; WaxOn had neither, though its Original Files entry says "A preset does not change this setting". The 2.16.0 changelog's "the in-app Help describe[s] this change" held only for WaxOff. WaxOff's Quick Start also called the toolbar "the header".

**F-M4 · `README.md`, `docs/index.html`** — Split L/R, 2.10.0's headline feature, is in neither front-door document; the README also lacks Original Files (2.16.0). The same pattern as the 2026-08-25 audit's F-M1/F-M2 for episode metadata.

**F-M5 · `docs/manual/index.html:739-741`, `HelpView.swift` Output Naming** — Split L/R's file names (`interview-L-44kwaxon.wav`, `OutputAllocator.swift:39-41`) appear in neither naming section.

## 4. Resolution

All findings except F-L1 are fixed on `claude/doc-drift-2026-11-06`, together with a `[Unreleased]` changelog entry. The wording for WaxOn's ceiling follows the theory page's "The −1.0 Ceiling, and What Kind It Is" section, which was right. The theory page's Summary gains a row for WaxOn's single measurement beside WaxOff's two-pass row.

The WaxOn screenshot was reshot from a Debug build of this branch at the same 1293 × 870 pt window, Edit Prep, sidebar open, with a synthesized speech file (`say`, with pauses and a quiet pink-noise floor) so that no recording of anyone's is published. The app's settings domain was exported before the run, staged for the shot, and restored afterwards; an export after the restore matched the backup exactly.

**For next time:** a behavioral change to one mode needs a search of every document for that mode's name next to the old mechanism (`grep -n -i 'waxon' … | grep -i 'loudnorm\|dBTP\|two-pass'`), not a read of the paragraphs that first came to mind. That one search finds every WRONG sentence in this audit.

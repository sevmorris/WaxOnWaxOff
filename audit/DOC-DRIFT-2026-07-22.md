## 2. Findings

### WRONG

---

**F-W1 · WRONG · theory `#edge-cases` ("Multichannel Input")**

**Doc claims** (theory.html:1221):
> "Stereo output passes all channels through unchanged up to the output channel count setting."

**Code does:** with Channels = Stereo, WaxOn's first FFmpeg stage always passes `-ac 2` ([AudioProcessor.swift:158](../WaxOnWaxOff/Services/AudioProcessor.swift)); the stereo filter path is `highpass,(allpass),aresample` with no channel handling ([AudioProcessor.swift:133](../WaxOnWaxOff/Services/AudioProcessor.swift)). A 5.1/7.1 source is therefore **downmixed to 2 channels by FFmpeg's default matrix** — nothing is "passed through," and unlike the mono path (which logs "⚠ N-channel input — using mono downmix…", AudioProcessor.swift:149) **no warning is logged**. Additionally, a mono source with Stereo selected is duplicated to 2 channels by the same `-ac 2` — documented nowhere.

**Proposed fix** (exact replacement for the sentence at theory.html:1221):
> "Stereo output on sources with more than two channels downmixes to two channels via FFmpeg's default matrix; a mono source is duplicated into both channels."
(Pending F-CB1 decision — if a warning is added to the code instead, append "A warning is logged." Do not merge until that call is made.)

**Blast radius:**
- theory.html:897 (`#waxon-design`): "Stereo output passes both channels through unchanged." True only for 1–2-channel sources; needs a qualifier ("Stereo output passes a stereo source's two channels through unchanged").
- index.html:623 (`#waxon-settings`, Channels row): "Stereo passes both channels through unchanged." Same qualifier needed.
- index.html:677 pipeline stage 1 describes "channel selection if Mono output is selected" only — silent about >2-ch/mono sources under Stereo.
- In-app HelpView.swift:70 repeats the claim (out of audit scope — see Open Question 2).

---

**F-W2 · WRONG · theory `#analysis-vs-processing` ("Why They Can Differ") + `#summary` table**

**Doc claims:**
- theory.html:1076: "**FLOOR vs LUFS**: FLOOR uses 80 Hz high-pass filtered mono blocks; LUFS in the stats panel uses unfiltered K-weighted audio."
- theory.html:1264 (Summary table, "Noise floor estimation" row): "10th percentile of 80 Hz HPF mono block RMS…"

**Code does:** the FLOOR high-pass cutoff is **not a flat 80 Hz**. In WaxOn it tracks the High Pass toggle — `fileQueue.noiseFloorHighPassHz = settings.highPassEnabled ? 80 : 20` ([ContentViewModel.swift:55](../WaxOnWaxOff/ViewModels/ContentViewModel.swift)) — exactly as `theory.html#noise-floor` (line 762) correctly states. This resolves the internal contradiction: **the `#noise-floor` "Estimation Method" section is the correct one; `#analysis-vs-processing` and the Summary table are wrong.**

**WaxOff cutoff (previously undocumented either way):** `DeliveryViewModel` never sets `noiseFloorHighPassHz`, so WaxOff analysis always uses the default **80 Hz** ([FileQueueCoordinator.swift:28](../WaxOnWaxOff/ViewModels/FileQueueCoordinator.swift)). See F-M2.

**Nuance worth capturing in the fix:** the cutoff is sampled when a file is analyzed at load time. Toggling High Pass afterwards does not re-analyze already-loaded files, so a loaded file's FLOOR reflects the toggle state at the moment it was analyzed.

**Proposed fix:**
- theory.html:1076 → "**FLOOR vs LUFS**: FLOOR uses high-pass filtered mono blocks (80 Hz or 20 Hz, tracking the WaxOn High Pass toggle; fixed 80 Hz in WaxOff); LUFS in the stats panel uses unfiltered K-weighted audio."
- theory.html:1264 → "10th percentile of HPF'd mono block RMS (cutoff tracks the WaxOn High Pass toggle; 80 Hz in WaxOff) identifies background noise level. …"

**Blast radius:** F-W3 (same subsystem), F-M2 (WaxOff cutoff), index.html:920 (manual FLOOR cell — states the method without any cutoff; acceptable as-is or extend while in the file).

**F-W3 · WRONG · theory `#noise-floor` (WaxOff paragraph)**

**Doc claims** (theory.html:774):
> "WaxOff still computes and displays the same FLOOR value — the measurement is identical to WaxOn's — and only withholds the warning/critical styling."

**Code does:** identical only while WaxOn's High Pass is on. With WaxOn's HPF off, WaxOn measures FLOOR through a 20 Hz filter and WaxOff through 80 Hz (ContentViewModel.swift:55 vs. FileQueueCoordinator.swift:28 default, never overridden in DeliveryViewModel).

**Proposed fix** (replace the quoted clause):
> "WaxOff still computes and displays the same FLOOR stat — measured with a fixed 80 Hz cutoff, matching WaxOn's default — and only withholds the warning/critical styling."

**Blast radius:** F-W2, F-M2.

**F-I1 · INCONSISTENT · Dynamic Leveling maximum gain: "≈ +15 dB" (manual, ×2, + in-app tooltip) vs "≈ +15.6 dB" (theory)**

**The three statements:**
- index.html:648 (`#waxon-settings`, Strength row): "a larger maximum gain (≈ +15 dB)"
- index.html:683 (`#waxon-pipeline`, stage 2): "maximum gain factor (`m` 2.0→6.0, ≈ +6 to +15 dB)"
- theory.html:873 (`#dynamic-leveling`): "**Max gain (`m`)**: 2× at Gentle, 6× at Aggressive (≈ +6 dB to +15.6 dB)"

**Code does:** `m = 2.0 + amount × 4.0` → 6.0× at Aggressive ([AudioProcessor.swift:439](../WaxOnWaxOff/Services/AudioProcessor.swift)); 20·log₁₀(6.0) = **+15.56 dB**. Theory is correct; the manual's "+15" is a loose rounding of the same number.

**Proposed fix (recommend aligning on theory's value):**
- index.html:648 → "a larger maximum gain (≈ +15.6 dB)"
- index.html:683 → "(`m` 2.0→6.0, ≈ +6 to +15.6 dB)"

**Blast radius:** the in-app Strength tooltip also says "Aggressive +15 dB" ([WaxOnControlBar.swift:42](../WaxOnWaxOff/Views/WaxOnControlBar.swift)) — code, not doc; flagging only (Open Question 2).

**F-I2 · INCONSISTENT · RNNoise model provenance: theory vs `Vendor/README.md`**

**F-M1 · MISSING · Batch output-collision naming absent from the manual (WaxOn) and from all docs (WaxOff)**

Code: when two batch inputs would produce the same output name, `OutputAllocator` inserts a 6-hex path-hash tag between the stem and the type suffix (e.g. `interview-a1b2c3-44kwaxon.wav`), with a UUID fragment as second-level fallback ([OutputAllocator.swift:40-71](../WaxOnWaxOff/Services/OutputAllocator.swift), [OutputNaming.shortPathTag](../WaxOnWaxOff/Services/OutputDirectory.swift)). This allocator drives **both** modes ([AudioProcessor.swift:38](../WaxOnWaxOff/Services/AudioProcessor.swift), [DeliveryProcessor.swift:63](../WaxOnWaxOff/Services/DeliveryProcessor.swift)).
Docs: theory `#edge-cases` (line 1226-1227) documents it **for WaxOn only**; the manual's `#waxon-output` and `#waxoff-output` sections say only "Existing files with the same name are overwritten" and never mention within-batch disambiguation. (Overwrite-on-disk is also true — pre-existing files are removed before the atomic move — the two behaviors coexist: the hash tag deduplicates within one batch; same-name files from previous runs are overwritten.)
Proposed: add one sentence to each Output Files section, e.g. "If two files in the same batch would produce the same output name, a short hash tag is inserted before the type suffix (`interview-a1b2c3-44kwaxon.wav`) so neither overwrites the other." Mirror for `…-a1b2c3-lev-18LUFS.wav` in WaxOff, and extend theory:1227 to note the same applies to WaxOff delivery names.

**F-M7 · MISSING · `dynaudnorm` pins `c=0` (channel coupling off)**

The filter string is `dynaudnorm=f=…:g=…:p=0.95:m=…:c=0` ([AudioProcessor.swift:443](../WaxOnWaxOff/Services/AudioProcessor.swift)) — pinned explicitly so behavior is stable across FFmpeg upgrades. ### CODE-BUG

Per the ground rules these are reported separately and no doc rewording is proposed to paper over them.

---

**F-CB1 · CODE-BUG (candidate) · Silent default downmix for >2-channel sources with Stereo output**

The documented design posture is that channel-destructive conversions are surfaced: the mono path logs "⚠ N-channel input — using mono downmix…" (AudioProcessor.swift:149) and the file list badges STEREO→MONO and MULTI→MONO conversions. But a 5.1/7.1 source processed with Channels = Stereo is downmixed to 2 channels by `-ac 2` with **no console warning and no badge** (the badge logic only fires when `outputChannels == .mono`, [FileListView.swift:45-48](../WaxOnWaxOff/Views/FileListView.swift)). Against the documented intent ("passes … through unchanged") and the mono path's behavior, the silence reads as an oversight rather than a choice. **Decision needed:** fix the docs to describe the downmix (F-W1's proposed text), add a warning/badge to the code, or both.

---

**F-CB2 · CODE-BUG (minor) · `DiskSpaceChecker` still budgets for a removed intermediate**

[DiskSpaceChecker.swift:10-16](../WaxOnWaxOff/Services/DiskSpaceChecker.swift) documents `waxOnTempMultiplier = 5` as covering "(4) normURL — optional loudnorm output", but the standalone pass-2 normalize file was eliminated in 2.2.0 (CHANGELOG: "fuses the pass-2 linear normalize and the 2× oversampled limiter into a single ffmpeg filter chain, eliminating one intermediate WAV write/read"). The current worst case is 4 concurrent intermediates (mid, dynleveled, NR temp, final tmp). Effect: the pre-flight gate over-reserves one file-size per concurrent job and can block a batch on a tight disk that would actually fit. Comment and multiplier both need the 2.2.0 update. Not user-facing except on nearly-full disks.
